### What problem does a "pattern" solve.   
An exact string answers a narrow question: "Is this text exactly `cat.jpg`?" Often we need a wider question: "Is this `any` JPEG file?" A **pattern** describes a family of strings that share a shape. Think of it as a fill-in-the-blank template.

A wildcard works like a Joke in a card game: it can stand in for something else. In a file search, `*.jpg` means "any name, followed by exactly `.jpg`."

### Glob vs Regex: two pattern languages
==There is more than one pattern language==. **Globs** are easy, limited language used by shells, file tools, and many URL matchers. Regular expressions (regex) are a more powerful, more complex language. Both describe a family of strings, but they use a different vocabulary.

| What you want         | Glob                   | Regex      |
| --------------------- | ---------------------- | ---------- |
| Anything              | *                      | .*         |
| Exactly one character | ?                      | .          |
| Ends in .jpg          | `*.jpg`                | `.*\.jpg$` |
| Starts with `api-`    | `api-*`                | `^api-.*`  |
| One digit             | No universal shorthand | `[0-9]`    |
Tip -> Before reading any pattern , ask : ==Which language is this tool expecting?== A correct glob pasted into a regex field may mean something completely different.

### The glob wildcards, one at a time.

| Wildcard | Name          | Description                                                                                                     |
| -------- | ------------- | --------------------------------------------------------------------------------------------------------------- |
| `*`      | Any run       | Matches zero or more characters. In path-style globs it often stops at `/.` Example: `item-*` matches `item-42` |
| `**`     | Deep Wildcard | Matches across everything, including `/` path seperators. Read it as "the rest, whatever it is."                |
| `?`      | Exactly one   | Matches one character-not zero, not two. `file-?.txt` matches `file-7.txt`                                      |
| `abc`    | Literal text  | Everything that is not a wildcard must appear exactly. Capitalisation may matter, depending on the tool.        |

For Playwright URL globs, `*` is the ordinary wildcard (it does not cross a `/` path seperator) , while `**` can cross seperators. In the bug later, the safest intent is simple: "match this known URL prefix and whatever comes after it," so trailing `**` says that clearly.

```Text
/user/*  ---> /user/42  -----> Accepted
/user/** ---> /user/42 ------> Accepted
/user/* ----> /user/42/posts -----> NOT Accepted
/user/** ----> /user/42/posts -----> Accepted (as ** crosses /)

A single star commonly stays inside one path segment, a double star safely matches deeper paths.
```

Note -> Glob dialects vary . A shell, `.gitignore` and a test framework may give `*` slightly different boundaries. Check the tools rules, use `**` when you deliberately mean "match the rest, including seperators"

### Anchoring: the invisible `^...$`
Anchoring means the pattern must cover the whole string, from  START to END. Imagine the invisible bookends around it: `^` marks the start and `$` marks the end.

```Text
/country/GBR?offerId=1111
^/country/GBR$ ----> NO MATCH
^/country/GBR.*$ (regex) ----> Match
/country/GBR** (glob) ---> Match
```

Key Idea ->
Anchored matching means : the pattern must account forn EVERY character. A pattern that ends where the real string keeps going will FAIL, silently. Adding a trailing wildcard `(**/.*)` means "and then I dont care what follows."

Gotcha ->
Many people assume patterns match "if the start lines up" (a prefix match). Anchored matchers do not --They need the whole thing. This mismatch between mental model and reality is exactly what caused the bug in Section 7.

### 6. How this shows up in test tools
HTTP mocking tools watch requests and ask: "Does this incoming URL match the route I should fake?" If yes , the test returrns a controlled response. If no, the request may go to a real server.

A **full URL** includes more than the path:
`https:// host.example /path/to/thing ?key=value&key2=value2`

The part after `?` is the ==query string==. It carries named values such as filters, ID and sort options.

Playwright's `page.route(urlGlob)` string glob is matched against the whole URL with whole-string semantics. If the glob ends at the path, an actual URL that continues with
`?query` is not fully covered. Cypress can avoid this particular trap by using an object matcher such as `cy.intercept({pathname: '...'})` , which targets only the path, the query can be checked separately.

| Tool/ Matcher              | What it sees                  | Practical Effect                                                             |
| -------------------------- | ----------------------------- | ---------------------------------------------------------------------------- |
| Playwright string glob     | Whole URL, whole-string match | Account for the host, path, and any query - often  with a trailing wildcard. |
| Cypress `pathname` matcher | Path only                     | The query does not change the pathname match; assert query value seperately. |
Keyidea- 
Match on the stable part (the path) and assert the variable part (the query) seperately. Dont bake volatile query strings into an anchored whole-URL glob unless you end it with a wildcard.

### 7. The exact issue found in YOUR test
 In `playwright/support/apiRoutes.ts` , the `promotionForecast` route constant ended at the country code
 ```
 ${PROMOTION_SERVICE}/v1/promotions/forecast/product/1010/period/10/country/GBR
 ```

But When the test clicks `View Forecast Matches`, `ForecastPanel.tsx` makes a GET request to that path _plus_ the axios params:
```
?offerId=1111111&storeFormat=UK&promotionReferenceID=1234
```

==Because Playwright applies whole-string matching to string globs, the route ending at `GBR` does not match the URL continuing with `?offerId=...`. The route handler never fires==

```
The whole URl was
 ${PROMOTION_SERVICE}/v1/promotions/forecast/product/1010/period/10/country/GBR?offerId=1111111&storeFormat=UK&promotionReferenceID=1234
 Our playwright matching happened till here -----------------------------------|     THE REST IS UNCOVERED HENCE - NO MATACH
```

There is no catch-all route , so the unmatched request escapes to the real staging backend with the dummy test token `CYPRESS_TEST_TOKEN`. The backend returns HTTP 401. A shared axios response interceptor from `@connect-shared-frontendend-utils/http-service`, wired through `src/config/axiosIntereptor.ts` , reacts by calling `window.location.replace(loginUrl).` That is the surprising "page refreshed to login" symptom

Important side effect-
The assertions inside the route handler - such as
`expect(query.get('offerId')).toBe('1111111')` - never run because the handles is never invoked. They are dead code during this failurem which is why they seemed 'off'

The fix-
```
 ${PROMOTION_SERVICE}/v1/promotions/forecast/product/1010/period/10/country/GBR**
```

Now the anchored pattern says "... GBR and then anything" . It matches the query-bearing URL, the mock fires and there is no escape , 401 , or login redirect. The CE forecast route in the same file already ends in `**` this brings the UK route in line with that convention.
This is safe: trailing `**` is strictly more permissive, so it still matches the bare `.../GBR`. Only one test file uses this constant, and there are no route-prefix collisions.

More Robust Alternative
Match by pathname and assert the query seperately, as the Cypress version does. That seprates stable routing from variable request data.

## Go deeper : concepts and resources

1. `Glob syntax` : Explore shell globbing, `fnmatch`, `.gitignore` patterns and Javascript libraries such as `minimatch` or `picomatch`. Why : each dialect teaches where wildcards stop and which extra feature exist
2. Regular expressions: Try `regex101.com` and learn anchors `^$` , character classes and quantifiers. Why : regex is the deeper rabit hole once globs make sense, and the visual tester explains each symbol.
3. Matching semantics : compare anchored vs unanchoured, full-match vs partial-match and APIs named test() vs match(). Why: the same pattern can give a  different result depending on how an API applies it.
4. URL structure (RFC 3986, at a high level) : learn scheme, host, path, query and fragment. Why: knowing exactly where the `?` query sits makes network matching much easier.
5. Playwright docs: Read Network/page.route , URL matching and page.pdf. Fun aside: this very PDF was made with playwright
6. Cypress docs: Read `cy.intercept` matchers, especially `pathname` and `query`. Why :its object matcher demonstrates how to seperate URL parts
7. Testing principles: "Match the stable, assert the variable" and "fail loud on unmocked requests." Add catch-all routes where appropiate. Why: a clear failure at the route boundary is much easier to diagnose than a distant login redirect.

One Last Mental Model->
Pattern language tells you what the symbol means. Matching semantics tell you how much the string must fit. URL structure tells you what string the tool is actually checking. Ask all three questions.
