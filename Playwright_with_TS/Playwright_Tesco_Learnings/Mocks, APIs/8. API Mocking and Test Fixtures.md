Terms:
1. mock/stub -> a canned response returned by a test code
2. intercept/route -> catch a request before it leaves the browser
3. fixture -> reusable canned data or a reusable test helper. The word has both senses
4. fulfill -> answer a caught request with a reponse
5. assertion -> a check that fails a test when it is false.

Some Mocking Code examples

1. Basic mock
```Typescript title="example.test.ts
intercept: async(pattern, data, status=200) => {
	await page.route(pattern, (route)) => 
	route.fulfill({
		status,
		contentType: 'application/json',
		body: JSON.stringify(data),
	})
	};
},	
```


2. Mock+verify query Parameters
```Typescript title="example.test.ts
interceptWithQuery: async(pattern,expectedQuery, data, status=200) => {
	await page.route(pattern, (route)) => 
	const query = new URL(route.request().url()).searchParams;
	
	Object.enteries(expectedQuery).forEach( ([key, value])) => {
		expect(query.get(key)).toBe(value);
	});
	
	return route.fulfill( {status, json: data});
	)};
},	
```

5. Delayed response
Holds the response for a given time before answering - useful for testing loading status
```Typescript title="example.test.ts"
slow: async(pattern, data, delayMs) => {
	awit page.route(pattern, aysnc (route)) => {
		await new Promise((resolve)) => setTimeout (resolve, delayMs));
		return route.fulfill( {status:200, json: data});
	});
},

```
Use it when: testing spinners, skeleton loaders or "this is taking a while"  messages - things that are invisible if the mock responds instantly

6. Dynamic request-based response
 The response body depends on what the request actually contained.
```Typescript title="example.test.ts"
dynamic: async(pattern, pick) => {
	await page.route(pattern, (route)) => {
		const result = pick(route.request()); // you decide the response from the request
		return route.fulfill({
			status: result.status ?? 200,
			json: result.body,
		});
	});
},
```

```Typescript test.ts
//Example usage: return a different promotion depending on the :id in the URL
await mockApi.dynamic (API_ROUTES.promotionById, (request)) => {
	const id = new URL (request.url()).pathname.split('/').pop();
	return {body: promotionById[id] ?? null, status: id in promotionsById ? 200 : 404 };
});
```

Use it when: one route pattern needs to behave differently depending on the id, method or payload - instead of registering ten near-identical `intercept` calls.

7. Sequential responses.
Returns a different body on each successive call to the same route - good for polling.

```Typescript title="example_fixture.ts"
sequence: async (pattern, bodies) => {
	let callIndex = 0;
	
	await page.route(pattern, (route) => {
		const body = bodies(Math.min(callIndex, bodies.length - 1));
		callIndex += 1 ;
		return route.fulfill( {status: 200, json: body});
	});
},
```

```Typescript title="example.test.ts"
// Example: a status-polling endpoint that goes PENDING -> PENDING -> COMPLETE
await mockApi.sequence(API_ROUTES.jobStatus, [
	{status: 'PENDING' },
	{status: 'PENDING' },
	{status: 'COMPLETE', result: { ok: true } },
]);
```
Use it when: testing polling UIs, progress bars, or anything that calls the same endpoint repeatedly and expects the answer to change over time.

 8.  Spy/ record
Mocks the response but also records every request made, for assertions after the UI action runs.
```Typescript title="myfixture.ts"
spy: async (pattern, data, status= 200) => {
	const calls: string[] = [];
	
	await page.route(pattern, (route)) => {
		calls.push(route.request().url());
		return route.fulfill( {status, json: data});
	});
	
	return calls; //caller inspects this array later, eg expect(calls).toHaveLength(2);
},
```

---
9. Pass-through + observe
Lets the real request go to the real network, but still records that it happend
```Typescript title="myfixture.ts"
observe: async(pattern) => {
	const requests: string[] = [];
	
	await page.route(pattern, (route)=>{
		requests.push(route.request().url());
		return route.continue(); // not fulfilled - forwarded to the real network
	});
	
	return requests;
},
```
Use it when: you're running a hybrid test against a real staging backend and only want to confirm 'this analytics/tracking call fired' without touching its response, or while incrementally converting a fully-live test into a mocked one.

## Part B - Bonus Gallery: More patterns to extend your creativity

10. Method-aware mock
One URL pattern, different behaviour per HTTP verb.
```Typescript title="myfixture.ts"
byMethod: async(pattern, handlers) => {
	// handlers = { GET: data, POST: data, DELETE: data }
	await page.route(pattern, (route) => {
		const method = route.request().method();
		const body = handlers[method];
		
		if(!body) return route.fallback();//let it through / 404 naturally
		
		return route.fulfill( {status: 200, json: body});
	});
},
```
Use it when: a REST resource like `/promotions/:id` is hit with `GET` to view and `DELETE` to remove - one registration covers both instead of juggling two seperate `page.route` calls with manual method checks.

11. Header verification
Confirms the app is sending required headers (auth tokens, content-type, correlation IDs)
```Typescript title="myfixture.ts"
interceptWithHeaders: async(pattern, expectedHeaders, data, status = 200) =>{
	await page.route(pattern, (route) => {
		const headers =  route.request().headers();
		
		Object.enteries(expectedHeaders).forEach(( [key, value]) => {
			expect(headers[key.toLowerCase()]).toBe(value);
		});
		
		return route.fulfill({status, json:data});
	});
},
```
Use it when: testing that auth tokes, feature-flag headers, or tracing headers are actually attached by your http client/interceptor - a common regression when someone refactors the axios/fetch wrapper.

12. Request body/ payload verification
For POST/PUT/PATCH calls - confirms the app sent the right shape of data.

```Typescript title="myfixture.ts"
interceptWithBody: async (pattern, expectedBodyMatcher, data, status= 200) => {
	await page.route(pattern, (route) => {
		const sentBody =  route.request().postDataJSON();
		expect(sentBody).toMatchObject(expectedBodyMatcher);
		return route.fulfill( {status, json:data});
	});
},
```
Use it when: testing a form submission - confirm the payload the UI built (after validation, transformation, formatting) actually matches what the backend contract expects, before even worrying about the response.

13. Pagination-aware mock
A specialised version of "dynamic" (#6) that serves different pages from one in-memory dataset.

```Typescript title="myfixture.ts"
paginated : async (pattern, allItems, pageSize = 10) => {
	await page.route(pattern, (route)) => {
		const page = Number(new URL (route.request().url()).searchParams.get('page') ?? '0');
		const start = page_ * pageSize;
		const content = allItems.slice (start, start+pageSize);
		
		return route.fulfill({
			status:200,
			json: {content, totalElements: allItems.length, number: page_, last: start+pageSize >= allItems.length },
		});
	});
},
```
Use it when: testing a data grid's  "next page" / "load more" behavior without hand-writing a separate fixture file per page.

14.  Flaky / intermittent failure injection.
Fails every Nth call - useful for testing retry logic and resilience, not just the happy path.

```Typescript title="myfixture.ts"
flaky: async (pattern, data, {failEveryNth = 2, failStatus=500} = {}) => {
	let callCount = 0;
	
	await page.route(pattern, (route)=>{
		callCount += 1;
		if (callCount % failEveryNth === 0) {
			return route.fulfill( {status: failStatus, json: {message: 'Simulated flaky failure'} });
		}
		return route.fulfill({status: 200, json: data});
	});
},
```
Use it when: your app has retry-on-failure logic (common in polling or upload flows) and you want to prove it actually retries and eventually succeeds, rather than just giving up on the first error.

15. Call-count assertion helper
A thin wrapper around 'spy' (#8) that asserts a request happened an exact number of times.
```Typescript title="myfixture.ts"
expectCalledTimes: async (pattern, data, expectedCount, performAction) => {
	const calls: string[] = [];
	await page.route(pattern, (route)) => {
		calls.push(route.request().url());
		return route.fulfill( {status: 200, json: data});
	});
	
	await performAction(); // the test passes in the UI interaction to run
	expect(calls).toHaveLength(expectedCount);
},
```
Use it when: you specifically want to catch a bug class like 'duplicate network calls on double click' or "an effect re-fetching every render"- things functional tests often miss because the `data shown` looks correct even when the `number of calls` is wrong.

16.  Fixture factories with overrides (builder pattern)
Not a route handler - a companion pattern for the `data` you pass into any of the above.
```Typescript title="myfixture.ts"
export const buildPromotion = (overrides: Partial<Promise> = {}): Promotion => ({
	tpnb : '1234',
	country : 'GBR',
	offerStartDate: '2024-01-01',
	offerEndDate: '2024-01-31',
	week1Sales: 100,
	... override, // caller only specifies what differs from the default
});
```

```Typescript title="example.test.ts"
//Usage: each test only states what matters to it
await mockApi.intercept(API_ROUTES.promotions, [
	buildPromotion({ country: 'ROI', week1Sales:0}),
]);
```
Use it when: your fixtures (the data, not the route handler) start getting copy-pasted with 90% identical fields across tests - a builder keeps each test readable by only showing what's different about that scenario.

17. File/binary download mock
Mocks an endpoint that normally returns a CSV/PDF/blob rather than JSON

```Typescript title="myfixture.ts"
download: async (pattern, fileContents, filename, contentType='text/csv') => {
	await page.route(pattern, (route)=>
		route.fulfill({
			status:200,
			contentType,
			headers: { 'content-disposition': `attachment; filename="${filename}"`},
			body: fileContents,
		})
	);
},
```
Use it when: testing a "Download CSV/Export" button without needing a real life-generation backend - you still get to assert the browser received the right filename and content type.

18. Unroute/ cleanup helper
Removes a previously registered mock - important for multi-step tests when behaviour needs to change mid-test.
```Typescript title="myfixture.ts"
reset: async(pattern) => {
	await page.unroute(pattern);
},
```

19. GraphQL operation-based mock
REST matches by URL; GraphQL typically posts everything to one endpoint, so you match by `operationName` in the body instead

```Typescript title="myfixture.ts"
graphql: async (operationName, data) => {
	await page.route('**/graphql', (route) => {
		const body = route.request().postDataJSON();
		if (body.operationName !== operationName)  return route.fallback();
		return route.fulfill( {status: 200, json: {data}});
	});
},
```
Use it when: your backend is GraphQL rather than REST - the mental model (mock the response, optionally verify the request) is identical, only the matching strategy changes, exactly like the original guide's portability matrix shows for other frameworks.

## Part C - the subtle trap, recapped

If an `expect(...)` throws `inside` a route handler, `route.fulfill(...)` never runs - the request just hangs, the UI stays in a loading state, and an unrelated downstream assertion times out 30 seconds later with a confusing message. Conversely, if the app never sends the request at all, the handler never fires and its assertions are silently skipped (a false pass).
Safer alternative for a load-bearing request check:
```Typescript title="example.ts"
await mockApi.intercept(API_ROUTES.promotionForecast,  forecastMatches); // mock only (reusable)

const requestPromise = page.waitForRequest((r)=> r.url().includes('/forecast/product/'));
await promotionsHomePage.clickViewForecastMatchesBtn(); // trigger the call
const request = await requestPromise;

const query = new URL(request.url()).searchParams;
expect(query.get('offerId')).toBe('A885882'); //clear, fast , isolated failure
```
