## The two different "orders" - dont mix them up

| order Type                                                                   | When it happens                                                    | Does it matter?            |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------ | -------------------------- |
| **Registration order** (order of `mockApi.intecept()` calls)                 | During test _setup_ , before the page even navigates               | YES - critically important |
| Runtime call order (orde the app actually fires GET/POST/etc. while running) | while the test is _executing_ , driven by the app's real behaviour | NO - makes zero difference |
## What happens under the hood.
1. `page.route()` calls (which `mockApi.intercept() wraps) just **registers a function** in Playwright's internal list of handlers for that page.This happens once, synchonously, udring your beforeEach/setup code.
2. No actual network traffic has occured yet at this point - you're just building a static, ordered list.
3. Later, when the real app code runs and fires an actual request (whenever that happens, in whatever oder), Playwright intercepts it and walks the registered list for that URL, newest-first, calling each handler until one of them calls `fulfill/abort/continue` (stopping the chain) rather than `fallback` (continuing it).
4. This walk is `stateless between requests` - nothing about handling one request affects how the next request (even to the same URL) will be handled. Each request starts the walk over from the newest handler again.
